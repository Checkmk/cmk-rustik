15//! # Checkmk Kubernetes Monitoring
16//!
17//! Welcome to **the in-cluster component for Checkmk's Kubernetes monitoring.**
18//! Some might call this a Kubernetes "agent". As a code-name we call it
19//! _rustik_. Actually, not quite: By _rustik_ we refer to _all_ of the
20//! in-cluster components used for Checkmk monitoring of a Kubernetes cluster.
21//! But you are looking at the documentation for one piece (out of two):
22//! `metrics-cache`.
23//!
24//! `metrics-cache` is the heart of Checkmk's Kubernetes monitoring. It collects
25//! information from various sources, namely the Kubernetes API and the
26//! `metrics-fetchers` (the "other" component in _rustik_). It takes the
27//! collected information and makes it available to Checkmk in the form of
28//! pre-generated, pre-computed Checkmk sections (those `<<<foo>>>` things).
29//!
30//! ## How sections get generated
31//!
32//! 1. Information enters `metrics-cache` from several sources:
33//!    - **The Kubernetes API** (via [watch]): structural data about the cluster
34//!      such as which pods are running, numbers of replicas, phases, resource
35//!      requests and limits, etc. This information is managed by the use of
36//!      [reflectors](kube::runtime::reflector()), a concept native to the
37//!      `kube-rs` library on which we depend.
38//!    - **The `metrics-fetcher`s**: real-time usage data (how much RAM/CPU is
39//!      each container in a pod using? -- from which we can also derive Pod
40//!      usage) storage usage and capacity, node health (also runs the Checkmk
41//!      openwrt agent... or at least some of it). Each `metrics-fetcher`
42//!      pushes into dedicated [`crate::handlers::ingest`] handlers which store
43//!      the data in a [`moka::future::Cache`] which lives in
44//!      [`crate::state::AppState`].
45//!
46//! 2. When section generation is triggered (via a request on the pull-mode
47//!    endpoint or the push-mode timer), an instantaneous
48//!    [`crate::snapshot::Snapshot`] is captured from the data collected in (1).
49//!    This means the data does not change out from under us while we are
50//!    generating sections, as the data in the caches in-memory can change at
51//!    any time. **Once the snapshot is taken, every other step relies on it,
52//!    never touching the raw live data.** The frozen API-data stores are
53//!    vectors of `Arc<K>` where `K` is the _[kind]_ of data the reflector is
54//!    watching. By using an [`std::sync::Arc`] here, we avoid needing to
55//!    duplicate every object we are watching, and we ensure it will stay around
56//!    in memory until we don't need it anymore.
57//!
58//!    As the snapshot is made, some internal data maps such as the
59//!    [`crate::snapshot::owner_graph::OwnerGraph`] and several
60//!    [`crate::snapshot::indexes::Indexes`] are constructed for fast
61//!    lookups during section generation. A
62//!    [`crate::ingest::reflectors::FrozenStores`] is where the snapshot of each
63//!    reflector data store is held in the snapshot.
64//!
65//! 3. Each kind we monitor is (or _can_ be) represented as a piggyback host.
66//!    As such, each has a `struct` representing it in [`crate::piggyback`].
67//!    The next step of section generation is that
68//!    [`crate::piggyback::emit_all()`] iterates the relevant frozen store and
69//!    constructs a piggyback host per object. The constructor of the piggyback
70//!    hosts acts as a filter in that it returns an `Option`. As an example,
71//!    [`crate::piggyback::namespace::Namespace::new()`] for namespaces returns
72//!    `None` for namespaces with no running or pending pod.
73//!
74//! 4. Each host emits its sections. The trait
75//!    [`crate::piggyback::PiggybackHost`] has a single method
76//!    [`crate::piggyback::PiggybackHost::emit()`] which returns the list of
77//!    sections emitted by each host.
78//!
79//!    The piggyback host's `emit()` will almost always call
80//!    [`crate::section::writeable::WriteableSection::of()`] which is where the
81//!    computed section data gets turned into a JSON `String` and stored for
82//!    render.
83//!
84//!    Importantly: Failures degrade gracefully; failure to emit one section
85//!    does not affect other sections or ruin the whole output.
86//!
87//! 5. Lastly [`crate::section::writeable::frame()`] frames the data by grouping
88//!    the [`crate::section::writeable::WriteableSection`]s produced by the
89//!    piggyback host's `emit()`, and writing it to a writer in section format.
90//!
91//! [Checkmk documentation]: https://docs.checkmk.com/latest/en/monitoring_kubernetes.html
92//! [watch]: https://kubernetes.io/docs/reference/using-api/api-concepts/#efficient-detection-of-changes
93//! [kind]: https://kubernetes.io/docs/reference/using-api/api-concepts/#standard-api-terminology:~:text=All%20resource%20types%20have%20a%20concrete%20representation%20(their%20object%20schema)%20which%20is%20called%20a%20kind
94
